# 44 · 通话实施方案（局域网版）

> 2026-11-04。所有者决定：**先不考虑跨局域网，只做局域网内的互相发现、呼叫、通话和视频。**这一版不需要任何服务器。`43-video-call.md` 是调研和证据；跨局域网的方案暂缓，要点收在 §9。任务是 `36` 号文档的 CALL-*。
> 状态：只有方案，没有实现。“提议值”是我的提议，不是测出来的，所有者可以改。开发和测试由开发 Agent 做。

## 0. 一页纸

- **做什么：**同一局域网内 ThinkOS 设备之间的 1 对 1 音视频通话：互相发现、配对、呼叫、接听、通话、视频。
- **怎么做：**
  1. **发现：**标准的 mDNS / DNS-SD，用 **JmDNS** 库；备选是 SSDP 风格的多播（复用仓库已有的 `Ssdp.kt`）。**不用 NsdManager 浏览**（§5）。
  2. **信令：**两台设备直接互发签名的 JSON，用 HTTP POST，复用仓库里的 `HttpServer`。
  3. **配对：**两边屏幕显示同一个 6 位短码，各自确认，互存公钥；没配对的设备不能呼叫。
  4. **媒体：**libwebrtc，**不设任何 ICE 服务器**，只用本机地址候选；Opus 加硬件 H.264。
  5. **来电：**复用投屏的“唤醒屏幕并接管前台”。
- **不需要：**服务器、STUN、TURN、MQTT、公网、第二个网络。ADR-015（设备脱离 Server 独立运行）天然满足。
- **为什么先做这个：**价值最大、风险最小，不依赖打洞成功率；摄像头、编码、回声、发热这些硬件问题先在这里解决。

## 1. 范围

| 做（首发） | 不做（首发） |
|---|---|
| 1 对 1 音视频；ThinkOS 设备到设备；同一局域网 | 跨局域网（暂缓，§9） |
| 发现、配对；呼叫、接听、拒绝、挂断、忙；摄像头开关、静音 | 群聊、录制、屏幕共享、聊天消息 |
| 默认关；来电必须点接听；通话中有明显指示 | 手机或浏览器对端；免接听直接开通 |
| 找不到设备时可以手动输入 IP | 通话记录、任何遥测 |

## 2. 这个网络上已经验证过的底子

- 设备与 Mac 在同一 Wi-Fi 上 TCP 直连可用（拔电实验的空跑里，设备连回了 Mac）。
- 多播在设备上收发过：2026-11-01 从 Mac 发多播 `M-SEARCH`，设备回了描述地址（`docs/28`）。
- mDNS 通告被 Mac 的 `dns-sd` 发现过（AirPlay 的 37 项真机测试，`docs/28`）。
- 所以**这个网络**没有 AP 隔离，多播可用。**别的网络没有数据**，要有兜底（§5）。
- 摄像头、编码器、回声消除、发热的实测在 `43` §2。

## 3. 架构

```
设备 A                                             设备 B
┌ 通话页面（插件声明）tos.call.*
├ CallHost（OS，Kotlin）
│   ├ PeerDiscovery ─ JmDNS（备选：SSDP 风格多播）
│   ├ Signaling     ─ HTTP POST，签名的 JSON（复用 HttpServer）
│   ├ Pairing       ─ 屏幕短码，互存公钥
│   └ WebRTC PeerConnection ─ 无 ICE 服务器，本机地址候选，DTLS-SRTP
└ 摄像头 / 麦克风 / 扬声器 / 屏幕
       ◄──── 发现：多播（同一局域网）────►
       ◄──── 信令：HTTP（局域网直连）────►
       ◄═════ 媒体：UDP（局域网直连）═════►
```

## 5. 发现

- **服务类型 `_thinkos-peer._tcp`。**不用 Server 设计里的 `_thinkos._tcp`（`docs/05` §2）。TXT 只放协议版本、名字、公钥指纹的前 8 字节；端口在 SRV 里。
- **默认关；关时什么都不做。**打开后才开监听、通告、多播锁（`CastHost` 已有多播锁的写法）。
- **只服务私网来源**（复用 `LocalNetworkPolicy.privateAddress`），解析一律有界，要畸形输入测试（`AGENTS.md`）。
- **为什么不用 NsdManager 浏览：**
  - Matter 项目的 issue #23709（Android 9）：解析器一次只处理一个，第二个请求报 `FAILURE_ALREADY_ACTIVE`；解析器“停不下来”也不会超时，超时后一直忙，要重启应用才恢复。这对常亮的设备是坏的失败方式。
  - AOSP 的一个提交（O-MR1）在 `discoverServices` 前加了多播锁，提交说明写的是以前解析不出服务；因果是我从说明里推的，没看到根因的明文。
  - 仓库里现有的 NsdManager 只用于**注册** AirPlay，没有浏览代码；浏览没有在这台设备上验证过。
- **JmDNS 的未知：**与系统 mdnsd（AirPlay 用 NsdManager 注册）在同一台设备上并存时，主机名会不会冲突（冲突会自动改名，应当无害，没验证）；在API27上的运行表现仍待。JmDNS3.6.5 JAR已静态核对220,480字节、Java8、Apache-2.0及SLF4J-api2.0.7依赖；与该依赖的离线D8成功不替代真机发现。
- **备选 SSDP 风格：**`NOTIFY` alive / byebye 加 `M-SEARCH`，`NT` / `ST` 用 `urn:thinkos:device:peer:1`，`LOCATION` 指向 `/call/v1/info`。复用 `Ssdp.kt` 的报文逻辑，发送搜索的一方要新写（很小）。
- **决定方式（CALL-0 的发现验证）：**两台真机互相发现不超过 5 秒、重启 20 次全部成功、24 小时后仍可被发现（提议值）。JmDNS 通不过就换 SSDP。

## 6. 信令与安全

- **端点**（同一个 `HttpServer`）：`GET /call/v1/info`（名字、版本、公钥指纹）；`POST /call/v1/pair/*`；`POST /call/v1/invite`、`answer`、`decline`、`cancel`、`bye`。
- **消息：**JSON，不超过 16 KB（提议），每个来源限速，同时只有一个通话（忙回 409）。`invite` 带完整的 SDP offer（等 ICE 收集完成再发），`answer` 同理，被叫在用户点接听后 POST 回主叫的监听端口。
- **签名：**对 `callId ‖ 计数器 ‖ SHA-256(sdp)` 做 ed25519 签名，用配对时存的公钥验。**没配对的设备只能访问 `info` 和 `pair`**，`invite` 一律拒绝。
- **防重放：**设备**没有 RTC**，不用时间戳；每对设备一个单调计数器加一次性的 `callId`，计数器持久化。
- **不加密信令**（局域网，SDP 不是秘密），但签名把 DTLS 证书指纹绑到配对的公钥上，局域网内的主动中间人换不掉它。
- **响铃超时：**约 45 秒无人接听就取消（提议值）。
- **配对（短认证字符串）：**两边各生成随机数，先交换承诺，再交换随机数；6 位码由两把公钥和两个随机数算出；两边屏幕显示同一个码，用户确认一致才存公钥。连续输错或拒绝若干次后锁定一段时间（提议 5 次）。要严格做主机测试，这是整个信任的根。
- **限度：**局域网内的恶意设备可以反复发配对请求骚扰（靠锁定缓解），也可以洪泛 HTTP 端口（靠限速缓解）；这里没有对抗网络层拒绝服务的设计。

## 7. 设备端

- **摄像头：**CallHost 是唯一使用者，结束时彻底释放（`docs/10` §5）。`dumpsys` 报硬件级别 3，`Camera2Enumerator.isSupported` 预期为 true；后备 Camera1。**在应用里复核。**
- **方向：**前置摄像头朝向 270°，屏幕是横屏倒装的（`docs/07` §9）。对端看到的画面必须是正的，本地预览要镜像。要在 CALL-0 验证。
- **音频：**`MODE_IN_COMMUNICATION`；平台对 `voice_communication` 预置了 `aec` 和 `ns`（`/vendor/etc/audio_effects.xml`），与 WebRTC 自带软件回声消除二选一，CALL-0 对比。ROM 里有 JamesDSP、ViPER 一类音效库（`/vendor/lib/soundfx/`），**可能干扰通话音频和回声消除，没测**。
- **发热与性能：**480p 起步；温度或掉帧超限就降分辨率，再降到纯音频；时钟优先（ADR-029），通话后跑时钟精度测试。
- **库按需加载：**`System.loadLibrary` 只在打开通话页或来电时调用，保证冷启动 < 3 秒。
- **权限：**`CAMERA`、`RECORD_AUDIO`，现在的清单两者都没有；运行时授权在引导里处理，Device Owner 可授权。
- **设置 schema：**`call.enabled`（默认关）、`call.name`（默认带公钥指纹后几位，避免名单里一排 ThinkOS）、视频分辨率上限；11 种语言。
- **界面：**按 ADR-044，不加说明文字。附近设备列表、来电、通话中三种页面；通话中控件：静音、摄像头开关、挂断、音量。

## 9. 暂缓：跨局域网

所有者 2026-11-04 决定先不做。恢复时的起点（证据在 `43` §4–§6）：

- 连接：ICE 加 STUN。STUN 用内置至少 150 个的列表，设备端健康评分，通话前并行问 3–4 个，经签名目录更新，不依赖 Google（实测 216 个候选里 107 个可用）。
- 会合：一台机器跑现成的 Mosquitto 加 `coturn --stun-only`，不转发音视频；信令消息格式（签名的 JSON）可以原样走这个通道，所以局域网版的设计不堵死这条路。
- 没有 TURN，打不通就明说；NAT 自检呼叫前提示。
- 备选：EasyTier 去 VPN 化（四项门槛见当时的方案）；BitTorrent DHT 兜底。
- **有没有完全不搭服务器的跨网办法：**有三种，都没验证成功率：BitTorrent DHT（没有运营方，要引入 jlibtorrent，armv7 的 .so 11.06 MB）、EasyTier 的社区共享节点（别人运营）、手动交换连接码（只适合两台设备在一起时）。
- 暂缓的任务：CALL-0b、CALL-1、CALL-3、CALL-4；OWN-19、OWN-20、OWN-23、OWN-24。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 别的网络开了 AP 隔离或不转发多播，发现失败 | 记住上次地址、手动输入 IP、提示检查路由器；这个网络没有这个问题 |
| JmDNS 在 API 27 上不稳 | 备选 SSDP 风格多播；发现放在接口后面 |
| 发热降频 | 分辨率分级，降到纯音频；CALL-0 的数据（配置里读不出门限） |
| 回声（单麦克风紧挨喇叭）；ROM 音效库干扰 | CALL-0 对比平台 AEC 与 WebRTC AEC，并测音效库的影响 |
| 画面方向、镜像不对 | CALL-0 专项验证 |
| 配对被骗（短码） | 承诺加随机数的短认证字符串；锁定；主机测试 |
| 局域网内骚扰（反复来电、配对请求、洪泛） | 未配对不能呼叫；限速；锁定 |
| 来电与 Kiosk、Lock Task、注意力状态机冲突 | 复用投屏的接管；CALL-2 前单独设计 |
| 隐私 | 默认关、接听、指示、硬件开关 |
| 许可 | CALL-0 核对 libwebrtc 内含第三方库和 JmDNS；`THIRD_PARTY_NOTICES.md` 登记 |
| 设备无 RTC | 防重放用计数器，不用时间 |

## 11. 所有者要做的事和总验收

**要你做的：**

1. 同意 ADR-047 里的澄清：通话不算“第二个播放器”。
2. 确认默认关、来电必须接听、不做免接听。
3. 指定**至少两台**实体机，在同一个 Wi-Fi 下做验证。**其余都不用准备：没有服务器，没有第二个网络。**
4. 确认 §8 里的门槛数字。

**总验收（P3）：**

- [ ] 同网通话 2 小时不掉线；弱网（丢包、带宽受限）下降级到低分辨率或纯音频，而不是断开。
- [ ] 24 小时待机保持监听和通告，CPU 和内存不超过基线 +20%（性能测试，先告知）。
- [ ] 时钟精度和冷启动 < 3 秒不回归。
- [ ] `AGENTS.md` 验收五条；`python3 -I -m unittest discover -s tools/tests`。
- [ ] 主机测试：信令和配对消息的畸形输入、重放、篡改、超长全部拒绝。
- [ ] 金镜像刷出的两台设备密钥不同。
- [ ] 许可登记完成；`docs/42-feature-rules.md` 加“通话”一节。

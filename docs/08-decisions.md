# 08 · 已定决策（ADR）

> 这里的结论**已经拍板**，开发时不要重新讨论；有异议请记录到本文件末尾的「待复议」区。

## ADR-001 用 View 体系，不用 Jetpack Compose

- **背景**：Compose 在 A53 + 2GB 上内存与启动开销偏高
- **决策**：使用传统 View + 自定义 View + Lottie
- **代价**：失去声明式 UI，需要手写状态绑定
- **依据**：设备性能基线（见 `docs/02-device.md`）

## ADR-002 不用 WebView 承载主界面

- **决策**：主界面必须是原生渲染
- **原因**：WebView 100 版在 A53 上实测卡顿；产品定位要求高帧率动画
- **例外**：不排除少量辅助页面（如设置里的外链）使用系统浏览器打开

## ADR-003 语音功能降级为可选模块

- **决策**：主链路不含语音；只保留唤醒词 + 5 个固定指令，且默认关闭
- **原因**：单麦远场拾音差；完整语音链路会与 UI 抢内存和 CPU
- **影响**：产品定位从「AI 伴侣」改为「桌面智能终端」

## ADR-004 摄像头采用三档策略（L0/L1/L2）

- **决策**：常驻 1fps 存在检测；仅在检测到人且近期有交互时开启 10fps 手势；拍照手动触发
- **原因**：持续手势推理会让 CPU 长期占用 40%+
- **收益**：平时占用降到 ~5%

## ADR-005 业务逻辑全部放在 Server 端 —— ⛔ 已被 ADR-015 取代

> 设备现在是自主运行的 OS，插件逻辑在设备上执行；Server 只负责下发、管理和可选的重活。以下保留原文作记录。


- **决策**：设备端只做渲染、采集、播放；不解析业务规则
- **原因**：设备算力弱；Server 端升级迭代不需要重装 APK
- **影响**：设备强依赖局域网，需要离线兜底（见 ADR-009）

## ADR-006 不依赖 Home Assistant

- **决策**：自建轻量服务，不引入 HA
- **原因**：HA 会带来沉重的运行时与概念模型；项目目标是独立的伴侣终端
- **例外**：可以**参考** kiosk-satellite / View Assist 的交互与实现，但不在运行时依赖它们

## ADR-007 自研 Kiosk Launcher，不用第三方底座

- **背景**：评估过 Fully Kiosk（闭源但成熟）、kiosk-satellite（需 HA）、DisplayLauncher（过小）、WallPanel（停更）
- **决策**：自研
- **原因**：需求（自定义动画 + 卡片系统 + 后续插件）任何现成壳都覆盖不了，最终都要拆掉
- **兜底**：开发期可临时安装 Fully Kiosk 保证设备可用

## ADR-008 插件在 Server 端运行，设备端只渲染 —— ⛔ 运行位置已被 ADR-015/016 取代

> 插件改为在设备上运行（声明式视图 + Lua）。**仍然有效的部分**：设备端只支持固定的渲染词汇，插件不能自造类型。


- **决策**：插件是 Server 端的进程/协程，通过卡片 JSON 下发 UI
- **原因**：设备无性能余量；插件沙箱更简单；任何语言都能写
- **限制**：设备端只支持固定的渲染词汇，插件不能自造类型（词汇范围已由 ADR-013 扩展为：页面版式 + 卡片模板 + 组件）

## ADR-009 必须支持离线兜底 —— ✅ 由 ADR-015 强化

> 离线不再是“兜底”，而是正常运行状态之一：插件在设备本地运行，Server 不在时功能完整（仅失去下发、通知中转与语音）。


- **决策**：与 Server 失联时，设备仍可用：时钟、本地相册（缓存）、本地音乐
- **原因**：Server 睡眠/重启时设备不能变砖头
- **实现**：最后一张卡片缓存到本地；离线状态显示右上角小圆点

## ADR-010 targetSdk 固定 27

- **决策**：`minSdk=27`、`targetSdk=27`
- **原因**：与设备一致，避免新行为差异（后台限制、存储、通知渠道）
- **代价**：无法使用需要更高 targetSdk 的库或 API

## ADR-011 客户端用 Kotlin 原生，不用 Flutter

- **背景**：考虑过 Flutter（开发效率、跨平台）
- **决策**：Kotlin + View 体系
- **理由**：本项目只有一台设备、一个平台，跨平台收益为零；而 2GB 内存、冷启动 <3s、Kiosk 系统 API、相机/音频链路都需要原生直连
- **代价**：界面代码不能跨平台复用

## ADR-012 服务端用 Go，插件走子进程 JSON-RPC —— ⚠️ 已由 ADR-015/016 修订

> Server 仍用 Go。子进程 JSON-RPC 只保留给**可选的 Server 端服务插件**（只提供数据，不提供界面）；功能插件改为设备上的 Lua 插件。


- **背景**：服务端在 Go / Rust / Python 之间选择
- **决策**：宿主用 **Go**；插件是**独立进程**，通过 stdin/stdout 交换 JSON-RPC 2.0
- **理由**：
  - 负载是 IO 密集（WS/HTTP/JSON），Go/Rust 都够；Go 的并发模型和开发速度更合适
  - 本机已装 go1.27.3，无需新工具链
  - 插件用子进程后**语言自由**（Python/JS/Go 都行），且崩溃不影响宿主
- **代价**：多一层进程通信；插件不能共享宿主内存
- **若将来需要重 CPU 处理**（如音频分析），用 Rust 写独立 sidecar，不重写宿主

## ADR-013 插件优先：页面即插件

- **背景**：产品需要像小爱一样靠插件加功能，且插件由别人编写、加功能不重装
- **决策**：ThinkOS 自身不实现任何具体功能。时钟、天气、相册、音乐、通知、首页**全部是插件**；每个整屏页面都是某个插件声明的 page，设备上左右翻页就是在插件之间切换。APK 只是运行时，提供 Lua 插件运行时、页面路由、舞台、动效、页面版式、卡片模板、播放器、感知（插件运行位置见 ADR-015/016）
- **原因**：功能迭代全部发生在插件里，不重装 APK；自带插件与第三方插件同一套接口，没有私有通道
- **约束**：插件只描述内容与语义，长相与动画由设备决定；渲染词汇只随 APK 升级扩展
- **来源**：用户决定（2026-10-29）。详见 `03-architecture.md` §2.1、`06-plugins.md`

## ADR-014 整机体验参照 iPhone「待机显示」（StandBy）

- **决策**：交互与观感以 StandBy 为蓝本：小组件 / 照片 / 时钟三个默认视图左右滑切换，上下滑切换样式；小组件为双栈智能叠放并按相关度轮换；实时活动全屏接管；通知以大图标出现；暗光下整屏变红的夜间模式；横屏为主形态；**白天浅色、夜里深色**，由环境光自动切换（手动锁定等设置见 ADR-017）
- **落地**：全部建立在 ADR-013 插件优先之上——三个视图分别是 `home`、`gallery`、`clock` 插件的页面；样式切换是页面的变体；夜间模式由设备在合成阶段统一处理，插件无感
- **来源**：用户决定（2026-10-29）。详见 `03-architecture.md` §2.2

## ADR-015 设备自主运行，Server 是下发与管理装置

- **背景**：旧模型里 Server 驱动设备的每一帧内容，设备离不开 Server
- **决策**：设备端 ThinkOS 是一个有自主性的 OS：插件、页面路由、状态、配置、照片集都在设备本地，**没有 Server 也能完整使用**。Server 的职责是：设备登记与配对、下发（插件包、配置、照片集、APK 更新）、中转（手机通知、远程指令）、可选增强（语音识别、Server 上的音乐库、Server 端服务）、观测（指标、日志、崩溃）
- **通讯**：从“Server 推画面”改为“期望状态同步”——设备通过 HTTP 拉取期望状态并在本地对齐、回报实际状态；WebSocket 只是可选的实时通道（nudge、通知、远程指令、服务调用、语音）
- **更新与仓库分发（ADR-041）**：设备可直接从配置的公开镜像或私网镜像读取签名更新目录、插件目录与内容寻址文件，不要求Server在线；Server仍可作为可选镜像和管理者下发自己管理的插件文件集。目录下载与验签属于OS原生能力，不由Lua的`tos.http`代行；已安装插件照常离线运行。正式钥匙/来源端到端、Server期望状态对齐的实施进度分别见`36-task-list.md`，此处不把协议设计当作已上线服务。
- **影响**：取代 ADR-005；ADR-008 的运行位置作废；ADR-009 强化；ADR-012 修订；协议见 `05-protocol.md`
- **来源**：用户决定（2026-10-29）。详见 `03-architecture.md` §1、§3.9、§4

## ADR-016 设备插件 = 声明式视图 + Lua 脚本

- **决策**：插件包由 manifest、声明式视图（JSON，用 `{{path}}` 绑定状态）、可选的 Lua 脚本和资源组成；没有逻辑的插件可以不写 Lua。脚本只能通过 `tos.*` API 访问能力，按 manifest 权限授予
- **原因**：声明式部分保证外观统一、横竖屏与动画由设备负责；Lua 轻量、启动快、内存小，适合 A53 + 2GB；在沙箱内运行，加功能不重装 APK
- **实现方向**：官方 Lua 5.4 源码随 APK 用 NDK 编译（只有 armeabi-v7a），自写 JNI 桥；所有 Lua 在单独的插件线程运行，带 CPU/内存预算（细节为提议，见 `03-architecture.md` §3.7、§9）
- **来源**：用户决定（2026-10-29）。详见 `06-plugins.md`
- **分发形态**：插件不再打成 `.tpk`（zip），改由 Git 仓库分发，见 ADR-018

## ADR-017 设置：系统级 + 页面级；外观不开放接口

- **背景**：希望 OS 能像 Apple Watch 那样被定制。评估过一套“部件样式系统”——表盘 = 固定部件类型 + 可换样式 + 槽位数据类型，再加样式包 / 表盘包生态——结论是**过于复杂**，且与目标相悖：在 AI 时代，想要什么样的页面，让 AI 写一个页面插件即可，不需要 OS 预留样式扩展点
- **决策**：
  1. **外观不开放接口**（ADR-025 修订：仅 `tile` 底色可由插件定义）。页面就是普通插件，长什么样由插件作者（或 AI）决定；OS 不引入样式语言、表盘包、部件皮肤等扩展点。ADR-013 的“渲染词汇只随 APK 升级扩展”保持不变
  2. OS 只提供**设置**，分两级：**系统级**（OS 自己声明，一份 schema）和**页面级**（每个插件在 manifest 的 `settings` 里声明）。两级共用同一种声明格式，类型只有 `bool` / `choice` / `number` / `text`
  3. 设置值由 OS 的设置存储保管：按 schema 校验、原子写盘，按“APK 默认值 ← Server 下发 ← 设备上修改”叠加，设备上的修改回报给 Server。插件只读（`tos.config`、`config` 事件），不能自己写
  4. **设置界面本身是插件**：内置 `settings` 插件按 schema 自动生成表单，与其他插件走同一套 `tos.*`，只多一个系统权限 `system.settings`（现阶段只授予 APK 内置插件）。OS 补充 `form` 页面版式，提供原生控件
  5. 入口：**长按任意页面**打开该页面所属插件的设置，设置页里可进入系统设置。**原生救援菜单**（隐藏的双指长按 5 秒）是唯一保留的原生设置界面，`settings` 插件不可用时自动回退
- **否决**：部件样式 / 表盘 / 样式包系统；复杂功能（complication）槽位与数据类型体系；长按编辑模式（长按改为进入设置）
- **影响**：manifest 的 `config` 字段升级并更名为 `settings`；`04-ui-spec.md` §9 由“以后要开放的设置”变为系统级设置清单；`09-roadmap.md` 新增 M0.5
- **来源**：用户决定（2026-10-30）。详见 `06-plugins.md` §11、`04-ui-spec.md` §9–10、`03-architecture.md` §3.18

## ADR-018 插件以 Git 仓库分发（取代 .tpk）

- **背景**：单个 zip 文件安装太麻烦；插件由第三方编写，最自然的载体是 Git 仓库
- **决策**：
  1. 一个插件 = 一个 Git 仓库里的一个目录（默认仓库根目录，也可用子目录）。**不再有 zip / `.tpk`**
  2. **设备不碰Git，也不直接访问作者仓库**。原有Server调用本机`git`取回、校验并按sha256逐文件下发的路径保留；ADR-041另增由仓库工具生成的签名目录与内容寻址文件，设备由OS原生客户端验证APK内置公钥、目录签名及逐文件摘要后安装，不需要Server在线。两条路径的已安装插件都可离线运行，来源隔离不得由Server清单缺项误删registry副本。
  3. **版本 = git tag**（SemVer，`v1.2.0` 或 `1.2.0`），安装时解析并锁定为 commit SHA（tag 可被改动，commit 不会）
  4. **发现 = 仓库 topic `thinkos-plugin`**（GitHub 的 Topics，不是 git tag）：GitHub、GitLab、Gitea / Forgejo（含 Codeberg）都支持按 topic 搜索。其它平台或私有仓库直接粘贴 URL 手动导入。搜索结果只是线索，能不能装以取回后的校验为准
  5. 安装前显示权限并由用户确认，更新新增权限需再次确认。**跟踪分支**（`main` 等）只开放给手动导入的插件，从搜索结果安装的一律按 tag
- **安全**：Server 只取回和校验，不执行仓库中的任何内容（无 hook、无脚本、无构建步骤）；不检出工作区，直接读 git 对象；拒绝符号链接、子模块、超限文件；传输协议限定 `https` / `http` / `ssh`；插件仍只能在设备 Lua 沙箱内、凭已确认的权限运行
- **影响**：ADR-016 中的“包”变成“文件集”；设备端安装器、APK 内置插件、`tools/plugin-push.sh` 全部改为目录形态（M0.5）；Server 的 `bundles` 模块改为 `registry`（M2）；V1 的“插件包签名”改为可选的 git 签名 tag 校验
- **来源**：用户决定（2026-10-30）。详见 `06-plugins.md` §12、`05-protocol.md` §3、`03-architecture.md` §3.7.5

## ADR-019 随 APK 携带 IANA 时区规则

- **背景**：设备 ROM 的 tzdata 固定为 2021a，无法正确处理其后各地调整的时区与夏令时。
- **决策**：APK 携带 `shared/tzdata/` 的 IANA 数据；`ZoneClock` 解析 TZif 与 POSIX 规则，所有插件时间格式与当地日边界都经此入口。系统时区 ID 仍由 Android 设置决定，不修改 ROM。
- **验证**：`tools/gen_tz_golden.py` 用 CPython `zoneinfo` 独立生成黄金向量，覆盖全部打包地区；未知 ID 只在普通时钟格式化时回退系统时区，天文地点的显式非法时区直接报错。
- **来源**：交接文档中已实现的设备约束与用户“日期时间跟随系统”要求（2026-10-30）。

## ADR-020 语言与日期时间遵从系统

- **决策**：系统字符串与内置插件提供 11 张语言表（含简繁中文）；按语言、脚本、地区逐级回退至英文。命名格式 `@time`、`@dateFull` 等由 OS 根据系统 locale 与 12/24 小时设置解析；插件不内嵌固定日期格式。格式化始终使用 ADR-019 时区规则。
- **边界**：系统设置、插件文案与无障碍文案走统一字符串源；外部 API 的原始地点名保留服务返回的本地化文本。
- **来源**：用户多语言与系统时间格式要求；补记交接时已有实现（2026-10-30）。

## ADR-021 本地位置与天文能力

- **决策**：位置保存在系统设置 schema。自动模式仅取设备时区的代表城市坐标，明确标记来源为时区推定；手动模式可选城市/区县或直接输入坐标与海拔。设备没有 GPS。在线搜索是可选辅助，失败不影响手填和天文计算。
- **能力**：`location` 权限允许 `tos.location.get()`、`tos.astro.sun(ms[, place])`、`tos.astro.moon(ms[, place])`；不依赖位置的 `tos.astro.seasons(year)` 无需该权限。日月计算在独立任务线程运行并挂起 Lua，结果回到插件线程；沿用挂起任务的预算、取消和所有权检查。结果为数据，可绑定 OS 组件，组件不向插件反向开放坐标。
- **时间与模型**：民用日期由自带时区库计算，涵盖 DST 的 23/25 小时及午夜空档。太阳事件按当天太阳中天前后各 12 小时的太阳窗口计算，月亮升落按当地日计算。几何高度与固定 34′ 地平折射分开；太阳上缘、海拔地平俯角、月球站心视差分别处理。月相时刻和月龄按真实黄经差求根，不使用平均朔望月。
- **验证**：计算模型与独立 PyEphem/libastro 黄金向量对照；不将测试库或 Python 带到设备。当前固定 ΔT=69.2 秒，面向 2020 年代；对外太阳/月球日期限定 2020–2050，季节计算限定 1950–2050。未授时设备返回空天文数据，界面显示占位。
- **来源**：用户要求日照/天文、城市（区县）位置及交接 §4-A/B；本地离线能力按 ADR-015 落地（2026-10-30）。

## ADR-022 设备持有媒体会话与播放队列

> 当前状态：已接线并在真机验收（ADR-030，API 7）。下面是当时的方向，网络策略与所有者模型至今有效，流媒体、HLS / DASH / RTSP 与影院视图的决定以 ADR-030 为准。

- **决策**：设备端采用 Media3 ExoPlayer 1.9.2，复用现有无原生库依赖；音视频共用一个 OS 媒体会话和队列。播放器操作在主线程，插件通过 `tos.media.*` 请求，队列索引对 Lua 从1开始，空队列为0。所有者被替换、移除或播放错误时收到事件。
- **状态**：OS 发布保留键 `media`，允许有媒体权限的页面直接绑定曲名、封面、进度及播放控制；插件只负责来源和数据，不逐帧更新播放器 UI。视频由原生 TextureView 承载。
- **网络与离线**：本地文件可离线播放；外部目录走 Android 运行时读取权限。网络媒体用 OkHttp 数据源，明文只允许私网地址，校验 DNS 与实际连接地址，拒绝 HTTPS 降级，沿用普通插件 HTTP 的同一规则。任何 Server 都是可选来源。
- **配置**：音量、循环、随机和来源等产品选项由插件或系统设置 schema 管理。播放器不引入另一份 SharedPreferences。
- **验证**：APK 检查只允许 armv7；队列与网络策略有单元测试；播放连续性、频谱 CPU/帧率和视频表现以真机记录为准，未实测不算完成。
- **来源**：用户要求 OS 提供音视频能力、插件解耦数据与显示；交接 §4-D（2026-10-30）。

## ADR-024 OS 图片接口与 Bing / 本地相册

- **决策**：API 3 开放 `image/carousel` 与 `tos.library.list`。Lua 只提供照片清单/文字与设置，OS 统一执行授权、边界检查、采样解码、EXIF、原生连续缓动平移、属性转场和生命周期；自带 gallery 不使用私有通道。
- **交互与流畅性**：用户进一步要求上下浏览历史和连续动画；carousel 统一提供上下拖动，手动首尾不循环，横向翻页和长按仍归 OS。平移改为原生属性动画，不再使用待机 5fps；方向随机，12 秒最短单程与 45dp/s 默认速度上限都经设置 schema。照片 float 时间采用白字与窄黑边。
- **完整画面**：按用户要求不永久裁图。`pan` 扫过整个溢出轴并按速度上限延长停留；`contain`、关闭平移或减少动画时整张缩放。无 Ken Burns 裁边；支持轮播、固定转场和字幕。
- **来源与边界**：用户补充要求微软每日一图后，gallery 默认设备直连 Bing，可选应用私有外部目录或合并来源；元数据只走公开 tos.*，网络图片下载和磁盘缓存归 OS 通用能力。Server 下发/管理、自定义 JSON 源继续暂缓。`controls/video/tos.media` 不随 API 3 自动解除暂缓。不增加 READ_EXTERNAL_STORAGE，不接权限弹窗或修改 Device Owner。
- **缓存与署名**：缓存先读，OS URL 缓存最多 50MiB/512 项，单 URL 合并下载、临时文件原子提交、显示中的文件不淘汰。Bing 清单独立持久化；title 与 credit 分开，署名不随字幕隐藏。公网 HTTPS/私网 HTTP 和重定向策略复用 MediaHttpClient。
- **安全和资源**：本地文件最终打开仍经 LibraryAccess 授权；单文件≤8MiB、≤32MP、长边≤8192，交付位图≤窗口像素×1.5 且≤2MP/长边4096。单 Decode 线程，当前+转场两张；离页/ASLEEP/Activity 停止取消任务并释放引用，旧插件代际不得回写。
- **来源**：用户“开发相册，暂不实现与上游服务通信”“图片不要裁，做平移和轮播，优先展现 ThinkOS 接口”，后明确“我的微软每日一图怎么没实现出来”（2026-10-30）。ADR-023 仍保留给未批准的 HTTP 通知提案。

## ADR-027 插件公开数据、公开指令与排版复用（2026-10-31）

- **状态**：接受，使用 API 6。用户要求插件能对外公开数据和排版，页面可直接使用相册的微软每日一图，模型类似 Home Assistant。播放器随后使用 API 7 / ADR-030（ADR-028 已用于 Start 屏）。
- **决策**：插件在 manifest 用 `exports` 显式公开状态路径，用 `uses` 声明读取，用 `calls` 声明调用的 `public` 指令。视图通过保留键 `{{uses.<alias>…}}` 绑定，Lua 通过 `tos.data.get`、`data` 事件和 `tos.command.call` 使用。`focus/split/stage` 槽位可引用 widget，`widgets[].alternates` 按模板提供呈现。
- **默认私有**：不开放整份状态。状态快照含设置值（包括 `secret`），且数据可能来自受权限保护的能力。导出路径不能进入 `config/uses/variant`；`requires` 要求读取方持有相同权限，防止权限转授。
- **图片授权**：只有整个值都是公开数据绑定时才按提供方授权加载，使用方拼接的地址按使用方权限检查。插件不接触图片字节，这样不会多暴露内容。
- **边界**：只有运行时路由，没有实体注册表、全局事件总线或自动化引擎。读取不触发提供方联网，也不唤醒它。全部在设备本地运行，不需要 Server（ADR-015），只走公开 `tos.*`（ADR-016）。使用方不能改被引用 widget 的外观（ADR-017）。不引入 HA 运行时（ADR-006）。
- **容错**：`shape` 带主版本，不兼容就断开而不是读错。提供方缺失时使用方为空并记录诊断，提供方恢复后自动重连。重启或升级保留已发布的值，避免闪空。指令有 `cooldown`，`data` 事件限速每秒一次。
- **来源**：用户提出设想并确认实现。接口见 `06-plugins.md` §6.8，验收见 `26-public-data.md`。

## ADR-028 Metro 开始屏：网格、背景、前景与动画词汇（2026-10-31）

- **状态**：接受，仍使用 API 6（API 6 尚未发布，新字段直接并入）。用户确认了开始屏效果图（`artifacts/tiles/concept/`），要求设备达到该状态，并要求系统级支持微软式交互小动画、由插件调用。目标是 Metro 风格的 concept，不是对 Windows 8.1 的逐项复刻。
- **网格（修订 ADR-025）**：横屏 8×6、竖屏 6×8，单元由短边决定（本机约 69dp），网格贴长边远端，余下约 142dp 为标题栏。OS 在栏内绘制页面标题（manifest 页面 `title`，语言切换时重新翻译）；栏太小则不画。默认开始页 10 张磁贴在两个方向都正好填满 48 格。
- **背景**：磁贴页使用 OS 固定背景：深色对角渐变加两道极淡的斜向光带，只绘制一次，不做动画。靛蓝 / 深青 / 酒红三种配色由系统设置 `tiles.background` 选择，默认靛蓝；不随明暗主题切换，插件不能提供或修改。三种配色上白字对比度均 ≥7.9:1。
- **前景（修订 ADR-025）**：白字优先；仅当白字对比度低于 4.55:1 才用黑字（此时黑字必然 ≥4.6:1）。夜间滤镜下按合成后的颜色同样判断。插件仍不能指定前景色，只有磁贴底色 `color` 是例外。
- **内容结构**：图标在左上，大号轻字重数字，名称固定在底部栏；宽磁贴多一行 `detail`。API 6 起：磁贴可带全幅 `image`（相册每日图），面（face）可带自己的 `content`（时钟的表盘在第二面）。`value` 在图片之上变为两行标题。图形、字号、间距全部由 OS 决定。
- **动画词汇**：
  - OS 自动：按下时朝触点方向倾斜（最大 7°，缩到 96.5%）并带过冲回弹；打开页面时磁贴依次升起入场（页面由手指拖入时不重复播放）；面切换沿用原有翻面。
  - 插件可请求：`tos.tile.animate(name)`，`name` 为 `pulse`（放大一下，新数据）、`flip`（立即翻到下一面）、`nudge`（左右抖动，拒绝/出错）。只作用于调用者自己当前可见的磁贴；同一插件同名动画 1 秒冷却；用户关闭“自动切换磁贴内容”（`tiles.live`）或系统关闭动画时一律忽略。无需权限、不开放时长、曲线或任何参数。
- **边界**：不是样式接口（ADR-017 不变）。不引入主题、皮肤、插件自定义字体或动画；没有新的插件权限；全部在设备本地运行，不依赖 Server（ADR-015）。
- **影响**：磁贴页的排布会比之前密（旧 6×4 页面在 8×6 里更小且靠右）；打包器按 8×6 / 6×8 检查放置。播放器随后使用 API 7 / ADR-030。
- **来源**：用户对开始屏概念图的确认与对“系统级小动画由插件调用”的要求。实现与验收见 `24-tiles-validation.md`。

## ADR-029 时钟优先（2026-11-01 提出，2026-11-02 补记正文）

- **决策**：显示的时间和秒数是整机最高优先级。任何动画、插件线程上的工作、页面切换、投屏、播放，都不得让它迟到、漏秒或显示过期的值。需要降级时先降别的动效，不降时钟。
- **度量**（`tools/tests/clock_accuracy_device.py`，在时钟页上跑）：连续 60 秒里每一次换秒，迟到 p95 ≤ 40 ms、最大 ≤ 80 ms、没有漏秒；显示的时间与对时服务器的偏差 ≤ 100 ms；进程重启后第一次读数就是对的；主线程被故意卡住约 700 ms 后，恢复时直接显示真实的秒（不显示过期的值，至多漏一次换秒），之后回到 p95 ≤ 40 ms。
- **怎么用**：新功能和新动画先评估对时钟的影响；涉及时钟页的验收，除了总体掉帧率，还要跑这个脚本。磁贴、相册、操作栏、投屏都按这个口径回归过。
- **来源**：用户“时钟的优先级是最高的，不能让任何卡顿影响时间，更何况我们还有秒级的时间显示”（2026-11-01）。编号 029 当天已被上面的设备脚本占用（ADR-030 的说明里提到），正文此前缺失，现补上。

## ADR-030 流媒体与影院视图（2026-11-01）

- **状态**：接受并已实现，使用 API 7（`tools/tests/clock_accuracy_device.py` 已把 ADR-029 用于时钟精度，所以本件取 030）。用户要求系统完整支持常见视频格式与网络串流，并在真机上验收。推翻 `22-player-plan.md` §1 / §9 里“不做 HLS / DASH、视频暂缓”的结论；ADR-022 的会话与所有者模型不变。
- **引擎**：仍是 Media3 ExoPlayer 1.9.2。新增 `media3-exoplayer-hls` / `-dash` / `-rtsp` 三个纯 Java AAR（无 `jni/` 目录，armv7 约束不受影响）。每个队列项按自己的 `type` 建 `MediaSource`（渐进式、HLS、DASH、RTSP 可以混在一个队列里），请求头、缓冲上限、字幕都按项处理。硬解 H.264 / HEVC / VP8 / VP9 / MPEG-2 / MPEG-4 / H.263 到 1080p60；轨道选择限制在 1920×1088 以内。
- **FFmpeg 音频扩展**：平台没有 AC-3 / E-AC-3 / DTS / ALAC 解码器，加入 `org.jellyfin.media3:media3-ffmpeg-decoder:1.9.0+1`（含 armv7 `libffmpegJNI.so`，1.36 MB）。版本比 Media3 低一个小版本，真机实测可用。**它是 GPL-3.0**，完整版 APK 带着它，整体按 GPLv3 发布（ADR-043）；`-Pthinkos.ffmpeg=false` 能出不含它的构建（这些格式会报“本设备无法解码 AC-3”，画面和其它音轨照常播放）。
- **接口（API 7）**：组件 `video`（影院视图）、`controls`（`mode`：`queue` / `seek` / `play`）、`seekbar`，需要 `media` 权限，安装器检查；`tos.media.*` 增加 `jump` / `live` / `audioTrack` / `textTrack`，条目增加 `type` / `headers` / `subtitles`，选项增加 `start`；`media` 状态增加直播、可拖动、缓冲、解码器、丢帧、音轨 / 字幕轨列表等字段；错误分类为 `network` / `http` / `notfound` / `permission` / `policy` / `format` / `decoder` / `audio` / `other`。完整字段见 `06-plugins.md` §6.10。
- **网络**：明文 HTTP 与 RTSP 只允许私网 / 环回 / 链路本地地址，沿用并加强 ADR-022；新增系统设置 `media.public_http`（默认关，只作用于媒体通道），打开后只放宽明文地址，HTTPS→HTTP 降级仍然拒绝。RTSP 自己开 socket，所以用自定义 `SocketFactory` 在每次连接前校验地址，并固定走 TCP 交织，RTP 数据不会绕过校验。请求头里除 `User-Agent` / `Referer` / `Accept` / `Accept-Language` / `Origin` 外的都只发给条目 URL 的同源地址（跨源重定向也会丢掉）；队列里的 HLS / DASH 项最多 16 个，因为 ExoPlayer 会同时准备队列里所有的项；RTSP 的 `user:pass@` 只存在于播放器内部，不进入状态和日志。
- **可靠性**：临时故障（超时、连接失败、HTTP / RTSP 408 / 429 / 5xx）按 1、2、4、8、15、15 秒退避重试六次，网络恢复时立即重试；对端断开的直播自动重连；掉出直播窗口回到直播点；缓冲 30 秒没有增长视为卡死，重连、仍不行则报错。不支持的编码一律给出明确错误（画面编码不支持 → 报错；只是音频不支持 → 画面照播并给 `warning`），不会静默黑屏或无声。
- **显示与注意力**：影院视图由 OS 绘制，触摸时浮出控件、无操作后淡出，字幕随控件让位；`ThinkStage` 为横向可拖动的组件（进度条）让出手势并解除长按计时，页面翻页、长按设置仍归 OS。视频播放时显示至少保持 AWAKE（`media.keep_awake_video`，默认开），暂停后恢复正常的变暗策略。画面上的触摸手势（2026-11-01 追加，无新增插件接口）：单击切换控件的显示，双击中间暂停 / 继续、左右四分之一跳 10 秒，竖拖左半屏调亮度（即 `display.brightness_max`）、右半屏调系统媒体音量；规则见 `27-streaming.md` §3.4。
- **页面**：`live` 页面（实时活动）不进入横向翻页序列，只能由插件接管进入，返回（最左缘右滑或 Back 键，ADR-040；原为左右滑动）回到接管前的页面。插件在用户点按自己页面的 5 秒内调用 `tos.page.focus`，不受“本地操作 30 秒内优先”限制（点一首歌就该打开播放页），ASLEEP 与设置页仍然拦截。
- **存储权限**：设备是 Device Owner 时，启动时用 `setPermissionGrantState` 静默授予 `READ_EXTERNAL_STORAGE`（读 `/sdcard/Music`、`/sdcard/Movies`），否则在首次访问时弹系统对话框。不申请写权限。
- **配置（ADR-017）**：`media.public_http`、`media.keep_awake_video`，隐藏项 `media.buffer_s`（30 秒，10–120）与 `media.buffer_mb`（48 MB，8–96）。缓冲上限是内存预算，不是偏好：ExoPlayer 默认给远程视频 125 MiB，本机放不下。
- **与 `22-player-plan.md` 的偏离**：不做 `nowplaying` 版式、歌词、频谱、`list.current`（本期只做视频与通用播放，音频页用 `focus` + `seekbar` + `controls`）；播放器是系统插件 `player`，取代 `music`。
- **边界**：不引入 WebView、Compose、GMS；不依赖 Server；没有新的插件权限名；DRM、RTMP、组播、SMB / NFS、站点解析（B 站 / YouTube 网页链接）不做。
- **影响**：APK 从 7.4 MB 增到 9.1 MB，其中 FFmpeg 扩展的 armv7 原生库约 1.4 MB（压缩后）。性能与验收记录见 `27-streaming.md`。
- **来源**：用户要求“为 ThinkOS 完整实现流媒体播放，支持常见视频格式、网络串流”，并确认设备已通过有线连接用于验收。

## ADR-031 投屏接收（2026-11-01，草案）

- **状态**：草案。**DLNA、AirPlay 视频推送、Miracast 投屏、AirPlay 屏幕镜像与声音都已实现**（`cast.enabled` / `cast.airplay`（`cast.airplay_mirror`）/ `cast.miracast`，默认关；真机上用脚本扮演的发送端通过 34 / 37 / 27 / 45 项检查）；**真实发送端里，macOS 与 iPhone Air 的 AirPlay 屏幕镜像已连上并有画面（2026-11-02）；华为的 Miracast、Windows、AirPlay 视频推送、各 App 的 DLNA 还没测**；确认页与 `tos.cast`（API 8）未做。用户要求利用 weekdayjast/MiracastReceiver 推进投屏接收，并明确沿用系统已有播放器。计划、取舍与验证记录见 `28-casting.md`。
- **决策**：协议层（DLNA、AirPlay、Miracast）由 OS 内的 `CastHost` 实现；播放一律走 `MediaEngine` 与 `video` / `controls` / `seekbar`，不引入第二个播放器。镜像来源用引擎内部的 `MirrorSource`（`MediaEntry.mirror`，只有 OS 能创建，插件不能构造；有界队列，满了丢最旧的）与低延迟缓冲档，并由 `MirrorPace` 追赶再生以压低延迟。协议不进 Lua。
- **发现身份（2026-11-03，WEL-4）**：DLNA UUID和AirPlay deviceid从应用私有的32字节随机种子派生，不读取ANDROID_ID；首次用到时生成，不依赖引导，和AirPlay配对密钥分开。金镜像必须省略ThinkOS应用数据中的种子，避免克隆身份；见`28` §16。
- **网络与安全**：监听只接受私网来源；推来的 URL 受 `media.public_http` 约束；总开关默认关；凭据不进日志与状态；日志里不写完整地址。全部在设备本机完成，不依赖 Server（ADR-015）。
- **参考项目的用法**：当协议层零件库，固定在提交 `d1aea7e`，MIT，重写（不复制代码），见 `THIRD_PARTY_NOTICES.md`。其 `playfair`（FairPlay）上游为 GPLv3，MIT 标签不覆盖；**完整版 APK 按 GPLv3 发布（ADR-034、ADR-043），所以 AirPlay 镜像与 FairPlay 做了**：`playfair` 与它的 GPLv3 许可证文本按原样纳入（来自 RPiPlay 的固定提交），见 `28-casting.md` §15。
- **已定**：Miracast 的系统权限由系统层模块的 root 守护进程行使（ADR-033）；音频只声明 AAC（ExoPlayer 的 TS 解复用读不了 WFD 的 LPCM）；视频只声明 720p 以内（面板 1280×800）。
- **待定**：镜像延迟关口要在真实 Source 上复测（模拟源上约 320 ms，关口 ≤ 约 400 ms）；AirPlay 视频推送在真实 iPhone 上要不要 FairPlay、要不要更多的 features；第一次连接要不要屏幕确认。
- **更正**：此前记录的“低延迟档 353 ms 过关”偏小约 0.5 秒（测试源的读取预热），更正后单靠缓冲参数是 870 ms，见 `28-casting.md` §8 ②。
- **来源**：用户“我准备继续推进项目的投屏接收功能……播放器我还是希望沿用我们系统里已有的播放器”与“开始进行”（2026-11-01）；“考虑到 root 权限和一些这个模块，我觉得我们 think os 不只是一个安卓应用，我们也是一套整体对安卓修改的方案，所以你在项目里也要增加一些这个模块的代码。我手上有华为和 iPhone。……开始实现，直到验收”（2026-11-01）。

## ADR-032 系统级单位设置（2026-11-01）

- **决策**：单位体系是 OS 提供的系统设置，不由各插件自带：`units.system`（`metric` / `imperial`，决定温度 °C / °F）与 `units.wind`（`auto` 跟随单位制 / `kmh` / `ms` / `mph` / `kn`）。设置页新增“单位”分组，沿用 §9 / §10 的 `choice` 就地展开行，没有新控件、没有新样式。
- **插件接口**：`tos.units.get()`、`tos.units.temperature(celsius)`、`tos.units.wind(kmh)` 只读且无需权限，变化时发 `units` 事件。插件内部一律用摄氏与 km/h 存数据和判阈值，只在显示时换算；换算在 OS 里做一次，保证各插件结果一致。插件不能写这些设置（ADR-017）。
- **取舍**：温度不单独成项，随单位制走；风速单独成项，因为公制地区常用 m/s 或节。降水、气压、距离等还没有用到它们的插件，用到时再按同样方式加词汇，不预先建空设置。
- **迁移**：天气插件移除 `temp_unit`，Server 下发的旧键会被当作未知键拒绝；需要时改下发 `units.system`。
- **来源**：用户“增加一个开关，控制单位体系是公制还是华氏，另外风速的单位是什么……系统提供的一套设置，所有插件也可以读取沿用”。

## ADR-033 系统层：Magisk 模块（2026-11-01）

- **决策**：ThinkOS 不只是一个安卓应用，也是一套对安卓的整体改动。需要系统权限的能力放进仓库的 `system/`，做成 Magisk 模块；第一个是 `thinkos-cast`（Miracast 的 WFD 元素）。应用一侧只通过一个很窄的接口（抽象 socket、三个命令）和模块说话，应用自己不 `su`。
- **为什么是 root 守护进程而不是别的办法**：`CONFIGURE_WIFI_DISPLAY` 是 signature 级，ThinkOS 的 APK 没有平台签名（重签名要重装，会丢掉 Device Owner）；这台设备的 `su` 只放行 adb shell。运行时 `su`（原参考项目的做法）会让一个解析漏洞变成 root，而应用要解析局域网里不可信的数据。
- **边界**：守护进程只认 root 与 ThinkOS 应用（`SO_PEERCRED`），只做写死的命令集，输入有界（256 字节一行、2 秒读完、名字只收可见字符）；应用一侧只相信 root 回的答案。**没有模块时应用照常工作**（ADR-015）：Miracast 不出现，别的不受影响。
- **谁做什么**：源码、构建、主机测试、在设备上不持久地跑一份来测试，都由开发 Agent 做；**把模块持久装进设备**（`system/install.sh`）、重启，由人工做（AGENTS.md）。
- **签名模块更新（ADR-041）**：上行是开发Agent的设备权限边界，不因存在更新器而改变。首次部署`thinkos-updater`与模块之外的恢复守卫仍由所有者完成；配置完成后的产品OTA由更新器接收固定协议/只读FD、先复制进root私有目录，再独立验系统根签名、固定七id、摘要与code防回退后执行受限事务，应用仍不`su`。源码/host/临时只读库存不等于真实模块升级通过；当前完整升级、重启与回滚仅在备用机验收，禁止装到HUA0BWUT，见`system/thinkos-updater/README.md`、`36-task-list.md` §0.7。
- **取舍**：守护进程不处理 P2P 连接请求（确认框由 Android 的 Wi-Fi Direct 栈弹出）；在 SELinux enforcing 下没有验证（设备是 permissive），带了一条被日志里的拒绝记录所要求的 `sepolicy.rule`。
- **来源**：用户“考虑到 root 权限和一些这个模块，我觉得我们 think os 不只是一个安卓应用，我们也是一套整体对安卓修改的方案，所以你在项目里也要增加一些这个模块的代码”（2026-11-01）。

## ADR-034 项目以 GPLv3 分发（2026-11-01）—— ⚠️ 已由 ADR-043 修订

> 项目自己的代码改为 MIT，只有完整版 APK 和 ADR-043 列出的部分是 GPLv3。原文保留；“以 GPLv3 分发”“`LICENSE` 放 GPLv3 全文”“给源文件加许可证头”和发布清单以 ADR-043 为准，`playfair` 的来源与风险评估仍然有效。

- **决策**：ThinkOS 开源后以 GNU GPL 第 3 版分发。
- **为什么**：AirPlay 屏幕镜像要求接收端用 FairPlay 握手拿密钥，唯一可用的实现 `playfair` 是 GPLv3（RPiPlay / UxPlay 里那一份，逆向苹果协议得来）；FFmpeg 音频扩展也是 GPL-3.0。项目一旦分发，含有 GPLv3 代码的整个应用就必须按 GPLv3 提供源码。用户明确选择这样做，而不是不做镜像或另找实现（没有许可证干净的替代）。
- **已落实的**：`playfair` 与它的 `LICENSE.md` 原样放在 `android/app/src/main/cpp/playfair/`，`ORIGIN.md` 写明来源提交；`THIRD_PARTY_NOTICES.md` 记录；`-Pthinkos.ffmpeg=false` 这个开关保留（想出一个不含 FFmpeg 的构建时仍可用），但不再是“为了能分发”必须关。
- **发布前还要做的**（这些不是开发 Agent 能替项目所有者决定的）：在仓库根放 `LICENSE`（GPLv3 全文）并给源文件加许可证头，版权人写谁由项目所有者定；逐项核对依赖的许可证与 GPLv3 兼容（已知的：Media3、OkHttp、Lottie 是 Apache-2.0，与 GPLv3 兼容；Lua、yyjson 是 MIT；MiracastReceiver 是 MIT；`assets/` 里的素材与字体、`server/` 的 Go 依赖**还没有核对**）；`playfair` 来自对苹果协议的逆向，除版权外是否另有法律风险由项目所有者自己评估。
- **来源**：用户“开源之后我会以GPLv3的许可分发”（2026-11-01），回答“AirPlay 屏幕镜像和音频为什么没有实现”时的决策问题。


## ADR-035 操作栏与应用（2026-11-02）

- **状态**：阶段 1 操作栏已实现，阶段 2 应用部分实现；实际进度和待验证项见 `29-panel-and-apps.md` §8。
- **决策**：从屏幕顶部下拉统一打开 ThinkOS 操作栏（媒体、亮度、音量、网络），取代安卓通知栏。操作栏是内置 Lua 插件 `panel`；手势、版式和控件归 OS，通过 API 8 的 `panel` 角色与版式、`slider`、`toggle`、`tos.device.*` 提供，新系统权限 `system.device` 只给 APK 内置版本。操作栏是叠层，不是页面切换，所以不触发 `page.leave`，投屏和播放不中断。
- **应用**：应用是 manifest 里 `apps[]` 的一个入口，指向插件自己的页面，不是新的运行形态（ADR-013 不变）；被指向的页面退出左右翻页序列，返回（ADR-040；原为左右滑）回到进入前的页面。`player`、`cast` 接入，新增 `tv`、`radio`、`apps` 三个插件。“广播”指网络电台。
- **安卓 App**：`tos.apps.*` 需要系统权限 `system.apps`。打开外部 App 时退出 Lock Task 但继续屏蔽通知栏，看门狗不拉回；因为 API 27 没有 `setLockTaskFeatures`，留在 Lock Task 里可能回不来。外部 App 上的下拉需要 `SYSTEM_ALERT_WINDOW` 和隐藏状态栏，放进新模块 `system/thinkos-shell`（ADR-033），没有模块时用 Home 键返回（ADR-015）。
- **边界**：不做通知中心、安卓App商店、FM收音；插件中心`hub`按ADR-041提供签名插件的浏览、确认安装与管理，不安装安卓App。不内置频道或电台；不开放外观参数（ADR-017）。（节目单原在此列，2026-11-02应用户要求做进了`iptv`，ADR-038。）
- **来源**：用户“把从上往下拉统一设置为启动这个操作栏”“我们可以把一些卡片或者页面定义为应用”“它可以打开安卓的其他 App”“操作栏也应该是一个 Lua 插件……系统要留出相应的接口”（2026-11-02）。

## ADR-036 音乐播放器视图（2026-11-02）

- **决策**：音乐界面由 OS 绘制一个组件 `nowplaying`（API 8）：整页 `full`、一行 `bar`、首页卡片 `card`，配套 `tabs` 和 `list.current`。插件只声明样式和两段文字（`idle`、`notice`），封面、取色、控件、音量条和队列都归 OS（ADR-017）；按钮、位置条、音量条、队列直接操作播放器，不经过 Lua（ADR-022、ADR-030）。需要 `media` 权限。
- **取舍**：没有新做 `nowplaying` 版式——变体沿用页面变体（上下滑），翻页动画沿用 OS 现有的整页滑动。没有封面图时按曲名画一张，颜色由曲名定；控件颜色按对比度求解（图形 ≥ 3:1、文字 ≥ 4.5:1），对全部 360 个色相做了测试。音量条改的是系统媒体音量（和音量键同一个，`DeviceLevels`）。队列取自引擎，不进 Lua 状态。一个组件只在**部分区域**算原生控件（`RenderComponent.interactiveAt`），其余区域仍归舞台，所以封面区还能上下滑切变体。

- **API**：编号冲突已解决，操作栏、音乐界面、电视和应用与返回统一并入 API 8（尚未公开发布）。

## ADR-037 沉浸式系统层：ThinkOS 在前台时不唤出系统栏（2026-11-02）

- **决策**：用一个 Vector（Xposed）模块 `system/thinkos-immersive` 钩住系统框架的 `PhoneWindowManager.requestTransientBars`，当前焦点窗口属于 ThinkOS 时让它什么都不做。其它应用里不改。
- **为什么**：从屏幕边缘滑动时，安卓会唤出状态栏和导航栏（顶、底、两侧共用这一个入口），不问应用；操作栏恰好从这条边缘拉下来，每次都闪一下。应用要免于这个行为需要平台签名的 `STATUS_BAR` 权限，Device Owner、Lock Task（API 27 没有 `setLockTaskFeatures`）、沉浸式标志、`policy_control` 都做不到；`user_setup_complete=0` 能让系统跳过它，但会连带动设置向导和 Device Owner 的前提，不能用。实测数据见 `29-panel-and-apps.md` §3.8。
- **为什么是 Vector 而不是 Magisk 模块**：这是改系统框架里一个 Java 方法的行为，不需要 root 守护进程；设备上已经有 Vector（`zygisk_vector`，`02-device.md`），不引入新的框架。
- **边界**：与 ADR-033 相同：源码、构建、主机测试归开发 Agent；装 APK、在 Vector 里启用并选“系统框架”、重启归人工（`system/install-immersive.sh`）。1.0钩子只会“放过”或“跳过”一次调用；ADR-045的1.1另外在其它应用底边上滑时发送一次无内容的显式通知，保留安卓原行为。任何意外都回到系统原有行为。**没有模块时应用照常工作**（ADR-015），只是边缘滑动时系统栏会闪约 1.5 秒。
- **代价**：Vector 2.2 在 Android 8.1 上，只要有启用的模块，守护进程就会在开机后一两秒崩（`PackageInfo.getLongVersionCode()` 是 API 28 的方法，没有模块时不崩，与本模块无关）；已加载的钩子不受影响，但之后 Vector 管理器和 `cli` 连不上，模块重装后它记的路径也没人更新。`install-immersive.sh` 因此在守护进程不在线时直接更正它数据库里的路径。换掉 Vector（或等它修了这个）之前，只能这样。
- **没做**：不隐藏外部应用里的栏（那里的返回键是离开安卓设置页等的路）；不改 `status_bar_height` 或 SystemUI；不把 Xposed API 作为依赖（`stubs/` 的替身只参与编译与主机测试，不进 APK）。
- **验证**：目标方法在这台设备的 `services.vdex` 里核对过；主机测试 10 项；APK 构建、签名与清单核对过；设备验收脚本 `tools/tests/immersive_device.py` 没装模块时 4 项滑动检查失败（基线）。**已在设备上启用并验证（2026-11-02）**：用户要求后由开发 Agent 装上（APK、`cli modules enable`、`scope set system/0`、重启一次），钩子加载，验收脚本 6/6，面板下拉时屏幕截图里没有任何栏；安卓设置页里的栏照旧。
- **来源**：用户“你能不能想办法禁用顶部的临时栏和底部的返回栏？这太影响我们的系统逻辑了”（2026-11-02）。

## ADR-038 电视直播：iptv 插件与 tv 组件（2026-11-02）

- **决策**：电视直播 = 自带插件 `iptv` + OS 组件 `tv`（API 8，随 API 8 一起发）+ Lua API `tos.media.probe`。插件决定播什么：读列表、合并、测线路、找节目单；OS 画电视界面：影院视图加频道横幅、节目与进度、下一档、上一台 / 下一台 / 频道列表 / 线路 / 收藏。按钮与手势只发一个事件 `tap(名字, 动作)`，动作是 `prev` `next` `list` `line` `favorite` 之一（ADR-017、ADR-022：不为外观开口子，不开私有通道）。
- **列表源解耦**：一个源种类是一个 Lua 模块（`sniff` + `parse`，`sources.lua` 登记）；`main.lua` 只认统一的 `{name, url, group, id, agent, referer}`。现有 `m3u`、`json`。插件不能读文件（ADR-016），所以列表都是地址。
- **合并**：按 `tvg-id` 或规范化名字（去括号、画质词、空格标点，CCTV 取台号）合并成一个频道多条线路；列表顺序优先，同列表里画质高的在前。≤600 个频道、每个 ≤6 条线路，插件状态与存储在 256 KiB 内。
- **线路测试与暂停**：每条线路一条健康记录，失败按 ×3 退避暂停（最长一天），到期再测；后台 `tos.media.probe` 每隔几秒测一条，收藏与最近的先；没测过的线路播前先看一眼；播放中失败立刻换线。离线保护：只有“没有任何应答”（刚读到列表、刚播上、服务器回过错误都算应答；都没有就再问一次第一个列表自己的地址）时才当网络断了、不记失败；网络通着时，不应答的线路（超时、地址不存在）算线路的错——一份满是死地址的列表否则永远测不出一条失效线路。一次性地址的源关掉“自动检测线路”。
- **为什么新增 `tos.media.probe`**：`tos.http` 按规定只放行私网明文，而电视源多是公网明文 http，用它测线路等于什么也测不了；探测改走播放的网络规则（`media.public_http` 等），读开头 16 KiB，不动当前会话。**为什么播前要看一眼**：播放器对回 404 的 HLS 列表会再问三次，真机上每条死线路让屏幕黑三秒多（`iptv_device.py` 量到的）。
- **为什么是 `tv` 组件，不是 `controls` 的 `events` 模式**（`29-panel-and-apps.md` 原方案）：上一台 / 下一台、线路、收藏要和节目与进度放在一起设计，做成一个组件，影院视图的手势、字幕与错误卡片原样复用，不引入第二个播放器。
- **节目单**：提供方可换（`guides/*.lua`）：XMLTV（列表头 `url-tvg` 或设置里填，整份读、存 6 小时）、每频道 JSON 的地址模板，以及央视网自己的央视节目表（`cntv`，只认央视频道）。受 `tos.http` 限制，超过 1 MiB 或 .gz 的读不了，页脚写明；ADR-035 的“不做节目单”因此改为“只做取得到的”。
- **边界**：不内置频道；默认只预置一个列表地址（下一条）；不做回看、录制、台标、本地文件列表。“应用”入口与磁贴由别的工作接上（`manifest.json` 的 `apps[]` 与 `tile`，ADR-040），本 ADR 不涉及。
- **预置的列表（2026-11-02，用户指定）**：`source_1` 的默认值是 `https://guovin.github.io/iptv-api/result.m3u`（Guovin/iptv-api 每天生成的公开列表）；其余列表默认空。预置的只是**一个设置默认值**：用户可以清空或改掉，APK 里没有列表的副本，设备第一次联网时自己去读（没有网络时这份公网列表本来也播不了）。**节目单只预置央视网自己的央视节目表**（`epg_url` 默认 `https://api.cntv.cn/epg/epginfo`，提供方 `guides/cntv.lua`）：该列表头里写的节目单是 404，项目自己留的 XMLTV 是 8 月的，常见的节目单服务在设备所在的网络连不上，只有央视网的接口连得上，见 `31-iptv.md` §10.2；卫视和地方台没有节目单。用真实列表在设备上试出来并修掉的：一个叫“2026-10-12 11:25:50”的假频道（带 CCTV-1 的 `tvg-id`，会把频道 1 改名并吞掉它的线路）；满是死地址的列表被旧的离线保护当成“网络断了”；设备字体不认的 emoji 分组名（🪁 画成空框，装饰 emoji 一律去掉，文字保留）；列表头里的 .gz 节目单不再去要；第一次读不到列表（GitHub Pages 在这台设备的网络上有时 3 秒内连不上）要等 6 小时才再读，现在读不到就按 30 秒起越来越长的间隔重试（30 秒、1、2、5、10 分钟，之后每半小时）。**需要用户决定**：这份列表 768 条线路里 518 条是公网明文 http（321 个频道里 143 个一条 https 都没有），`media.public_http` 默认关（ADR-022），不打开就有近一半频道播不了；没有替用户改这个默认。
- **验证**：Lua 65 项在 Mac 与 armv7 设备上通过（最长一片约 23 ms），Kotlin 单元测试、打包器、Go 协议测试通过；设备整条流程 `tools/tests/iptv_device.py`；详见 `31-iptv.md` §8。
- **来源**：用户“创建：iptv 电视插件，解耦列表源，合并相同节目，自动测试临时禁用失效源，尝试获取节目单，增加专属电视控件”（2026-11-02）。

## ADR-039 平等的插件与开放的界面（2026-11-02）

- **状态**：方向已定（用户）；机制是草案，细节、迁移步骤与止损条件见 `32-open-ui.md`。**没有写代码，没有上设备验证。**
- **决策**（用户的设计目的）：任何插件均平等；系统默认的 UI 和组件也由 Lua 插件实现；用户可以把它们换成自己想要的任何内容。落到实处是三条：
  1. **平等**：不为内置插件保留别的插件走不了的路。同一套 `tos.*`、同一套权限检查、同一套安装与回滚。出厂插件与别的插件唯一的差别是“已经装好、已经授权”。
  2. **界面也是插件**：页面、版式、组件（时钟、列表、滑块、音乐界面、电视界面、磁贴、操作栏……）都是插件里的 Lua 实现。APK 里只剩**机制**：Lua 运行时与沙箱、场景内核（绘制原语、信号、动画、手势）、能力服务、恢复外壳。
  3. **可替换**：用户在设备上选择哪个插件提供哪个角色 / 版式 / 组件，随时可以换回出厂；换坏了自动回退。
- **机制（提议）**：每个可替换的东西是一份有名字、有主版本的**契约**（`role/home`、`layout/tiles`、`component/clock`）；插件在 manifest 里声明自己**提供**哪些契约；系统设置 `ui.bindings` 决定用谁；解析顺序是用户绑定 → 出厂 → 内核占位。场景内核提供绘制原语、信号表达式、属性动画和手势识别，让按下反馈、跟手、翻页弹簧、时间驱动的运动都在原生里完成，Lua 只声明和决策（**反馈在原生，决策在 Lua**），所以 Lua 仍不进主线程，时钟仍不依赖 Lua。
- **取代 / 修订**：取代 ADR-013 的“渲染词汇只随 APK 升级扩展”；修订 ADR-017 第 1 条（仍然没有样式语言、主题文件、皮肤包，变的是“组件与版式只能由 OS 画”）；取代 ADR-017 第 4 条与 ADR-035 里“`system.*` 只给 APK 内置版本”（改为必须在设备上确认的强权限）；ADR-025 / 026 / 028 / 036 / 038 里“OS 画 tile / aero / nowplaying / tv”变成“出厂提供方”，Lua 版通过验收之前原生实现照常当默认。**与 `AGENTS.md` 的 4 条规则冲突（2 条直接、2 条措辞），等用户同意后再改**，拟议文本在 `32-open-ui.md` 附录 A。
- **不变**：设备自主（ADR-015）；Lua 不在主线程、预算不变（ADR-016）；时钟优先（ADR-029）；恢复路径不依赖插件（救援菜单、安全模式、出厂恢复保留为原生）；夜间滤镜、防烧屏、亮度与注意力策略仍由内核在合成层统一处理，所有插件同等受约束；只能 armv7、API 27，不用 WebView 和 Compose；没有样式语言。
- **前提与止损**：先做可行性验证 S1——用场景内核的最小切片重写时钟和滑块，过 ADR-029 的度量和 CPU / 内存 / 冷启动基线。不达标则退到“只开放由现有原语组合的高层组件与版式”，并把因此做不到的部分（例如自绘时钟表盘）交回用户决定，不悄悄降标准。
- **来源**：用户“设计目的：任何插件均平等，系统默认ui和组件也是lua插件实现，用户可以替换为自己想要的任何内容”（2026-11-02）。

## ADR-040 应用与全局返回手势（2026-11-02）

- **状态**：已实现，真机验证了触摸、按键与动画（`nav_back_device.py` 26 项通过）；性能还没测。设计、实现与验证见 `33-apps-and-back.md`。
- **决策**：
  1. 插件除了**卡片**（栈里的卡片、磁贴）和**页面**（翻页序列里的整屏），多一种展现形式：**应用**。应用默认全屏，不在翻页序列里，从磁贴、卡片或插件自己的请求进入；进入后左右滑动属于应用本身，OS 不再翻页，连边缘的橡皮筋位移也不做；不画翻页指示点。
  2. ThinkOS 增加一个全局手势：**从屏幕最左缘起手向右滑 = 返回键**。它和 `KEYCODE_BACK` 走同一条路：关操作栏 → 收起页面上的原生弹层 → 把 `back` 事件交给声明了拦截的应用 → 弹出返回栈。**翻页序列里栈是空的，最左缘右滑仍然翻页**，没有死区。
  3. 应用、设置页和实时活动页（影院视图、电视、音频播放页）统一用返回或 Home 键退出，不再靠左右滑。
  4. 导航状态收成一个**返回栈**（`NavStack`：应用、接管、设置三种层，深度 ≤ 8），取代 `DeckRouter` 里 `settingsReturn` / `previousLive` / `previousApp` 三个各管各的字段。
  5. 打开应用有一个 **Windows 8.1 风格的“翻转并启动”动画**，关闭时倒着放（`AppTransition`）：磁贴绕各自的左边缘翻走、点中的最后走，应用页绕屏幕左边缘翻进来。样式、时长、顺序归 OS（同 ADR-028，插件只能打开或关闭应用）；系统动画关闭或 `reducedMotion` 时不翻。
  6. 应用要自己接管返回（有自己的层级）时用 `tos.back.intercept(true)` 和 `back` 事件，不需要权限；收到 `back` 后 2 秒内毫无反应的应用被越过，不能困住用户。
- **名字**：用户把“程序”和“应用”合并成一个概念，**统一叫应用**（区别于“安卓 App”）。所以 ADR-035 的 `apps[]` 不改名；曾经设想过的 `programs[]` 作废。一个应用的页面不能带角色（`home` / `ambient` / `sleep` / `settings` / `panel`）。
- **第一批应用**：`player.library`、`iptv.channels`、`cast.home`（新建的等待页，带只读的 `tos.cast.status()`）。开始屏 48 格已满，所以 `tiles` 插件多一页 `tiles.apps` 放这三块磁贴。应用列表插件、`grid` 组件、`tos.apps.*` 仍属 `29-panel-and-apps.md` 阶段 2，不在本期。
- **修订**：ADR-030 的“左右滑动回到接管前的页面”改为返回；ADR-035 的“被指向的页面退出左右翻页序列，左右滑返回”改为返回手势退出；`MainActivity.onBackPressed()` 不再是空操作；调试广播 `page` 从翻页序列出发。
- **不变**：Home 键回主页并清空返回栈；顶部下拉操作栏；双指长按左上角的救援手势；长按进设置；变暗、夜间、睡眠对应用一视同仁（应用没有特权）；设备自主（ADR-015）；Lua 不在主线程；时钟优先（ADR-029）。
- **边界**：不做多任务切换，不做应用常驻的后台窗口；不做安卓 App 里的返回手势（属 `29-panel-and-apps.md` 阶段 4，要系统层模块）；外观仍按 ADR-017 / 039，应用的“全屏”和启动动画不是样式接口。
- **来源**：用户“另外，除了卡片，我希望为插件增加一种新的展现形式：程序；默认全屏，进入后左滑右滑不再切换其他页面卡片；为ThinkOS增加全局手势：从最左开始滑动：返回键”，随后“统一为应用吧”“视频、电视这类实时活动页也只靠返回退出：是”“翻页序列里从最左缘右滑：照常翻页”“第一批：`player.library`、`iptv.channels`、`cast.home`，这些需要实现”“启动应用时，应该创建一个 Windows 8.1 风格的动画（翻转并启动）”（2026-11-02）。

## ADR-041 OTA 更新与 GitHub 插件仓库（2026-11-02；2026-11-05更新状态）

> 界面用词按 DEC-6 / ADR-044：设备管理、Wi-Fi；面向用户的投屏提示称手机或电脑。以下保留原始决策记录。

- **状态**：方向已定（用户），代码已实现并分段真机验证，整条正式发布链路未验收。应用UID安装、崩溃回滚与600秒健康见 `artifacts/update/OTA-3/install/qualification.json`；Hub与插件基础签名安装见 `artifacts/registry/REG-2/0.1.8/qualification.json`。系统更新器/外置守卫已有源码、host及临时只读库存证据，未持久安装，完整模块OTA仍待备用机；正式公钥/来源与证书迁移、REG-2b完整生命周期仍待完成。独立审计及F1/F3主机修复见 `artifacts/update/OTA-6/`，F2仍开放；当前分层状态见 `34-ota-and-plugin-registry.md` 文件头，不把历史夹具检查当作正式来源端到端通过。
- **决策**：
  1. **不信任传输，只信签名**：设备只相信 APK 内置的公钥。公钥验证目录文档，文档写明每个文件的 sha256；文件从 GitHub、jsDelivr、局域网镜像还是将来的 Server 下载都一样。没有地方需要令牌。
  2. **OTA**：更新 APK、系统模块和官方插件。**免提示安装**：系统设置“自动安装更新”（`update.auto_install`）默认开，只在深夜没人用的安静时段装，模块有变化时重启一次；关掉后下载好等用户点，点了也没有系统确认框。Magisk、Vector 等第三方组件和 ROM 不走 OTA。
  2a. **系统模块经 `thinkos-updater`**：新的 root 守护进程，第一次由人工安装。应用只把文件交给它，**它用自己内置的系统钥匙独立验签**，只收白名单里的模块 id，防回退，不解析 zip，不接受任意命令。应用被攻破也拿不到 root。带启动守卫：坏模块下次开机恢复，新版不健康就自动回滚。
  3. **插件仓库**：独立仓库 `thinkos-registry`。作者提 PR，CI 校验并收录文件，生成签名目录；设备只读目录和内容寻址文件，**不碰 Git，也不碰作者的仓库**。安装前由 OS 弹原生确认框，新增权限再确认。
  4. **界面是插件，恢复是原生**：插件中心 `hub` 是内置 Lua 插件，只用现有词汇（ADR-039）；确认框和救援菜单里的更新入口是原生的，插件全坏了也能升级。
- **修订**：ADR-033（持久安装模块只有第一次要人工，之后由签名的 OTA 经更新器完成；对开发 Agent 的边界不变）；ADR-015（设备也可以直接从公开镜像取，Server 是可选的局域网镜像和管理者）；ADR-018 第 2 条与 `05-protocol.md` §11（设备读取签名目录，Server 取 Git 的路径保留）；`03-architecture.md` §4.3 的“不做静默安装”；`05-protocol.md` §3.2 的“`plugins` 是全集”（否则会删掉用户从仓库装的插件）；ADR-035 的“不做应用商店”改为不做安卓 App 商店。
- **不变**：设备自主（ADR-015）；设备端不引入 Git；应用里没有 `su`（ADR-033）；时钟优先（ADR-029），安装和重启是它唯一接受的例外，自动安装只在没人看的时段；Lua 沙箱与预算（ADR-016）；`system.*` 在 ADR-039 P1 之前只给内置副本。
- **前提**：公开发布完整版 APK 就触发 ADR-043 的发布清单，并且要同时公开完整源码；API 27 不能换证书，所以要先定正式证书；**系统钥匙等于所有自动更新设备的 root**，只放在 Mac 和离线介质上，永不进 CI；开放第三方插件前要先堵上角色抢占（目前只有 `panel` 角色有校验）；Magisk 27.0 的防重启循环不能指望，所以有自己的启动守卫。
- **依据**（设备 shell 实测，一个晚上的少量样本）：GitHub Release 下载 15–18 KB/s、`*.github.io` 不通、`codeload` 超时、Cloudflare 不通，jsDelivr 24–160 KB/s。所以不依赖 GitHub API 和 Pages，下载必须能续传、能换源。
- **来源**：用户“我想为 ThinkOS增加OTA更新功能、插件仓库（Github），帮我详细策划一下”；“系统模块也要参加ota，要实现免提示apk安装，在设置中增加选项 自动安装更新”（2026-11-02）。

## ADR-042 新用户启用引导（2026-11-02，草案）

> 界面用词按 DEC-6 / ADR-044：设备管理、Wi-Fi；面向用户的投屏提示称手机或电脑。以下保留原始决策记录。

- **状态**：方向已定（用户）；机制是草案，见 `35-onboarding.md`。**没有写代码，没有上设备验证**。
- **决策**：
  1. 第一次开机进入引导，**顺序仿照苹果的 Setup**，一屏只问一件事，用不上的屏自动跳过：你好、语言、地区（只有多时区的地区才多问一屏时区）、无线局域网、数据与隐私、专用设备模式（需要时）、软件更新（即“自动安装更新”）、位置、外观、手势、欢迎。一路继续约一分钟，加手势练习约两分钟。
  1a. **和苹果不同的地方**：可以不联网（ADR-015）；没有“同意条款”（GPLv3 第 9 条：接收和运行不需要接受许可证；MIT 也没有要用户同意的内容）；第一屏能跳过全部；文字大小暂不做；手势是真实练习，不只是看演示。
  2. **不强制、不困住人**：每步可跳过；不需要账号、网络、Server、系统模块（ADR-015）；插件坏了直接进首页；半小时没人碰就退出；半途退出下次开机再问，最多 3 次。老设备升级不出现。
  3. **引导也是插件**（ADR-039）：内置 Lua 插件 `welcome`，新角色 `onboarding`。步骤和文案在 Lua 里；什么时候进入、退出路径、手势识别归 OS。不加新组件和版式，给 `form` 加一个 `hero` 槽位和底部主次按钮，设置页不受影响。
  4. **手势练习**：OS 的练习模式照常识别手势但不执行，只报告做对了；画面归 OS，文字归插件。

## ADR-043 许可证分层：源码 MIT，完整版 APK 按 GPLv3 发布（2026-11-03）

- **状态**：接受（用户）。修订 ADR-034；ADR-030、ADR-031、ADR-041 的相关措辞已跟着改。根目录已放 `LICENSE`（MIT）和 `LICENSE-GPL-3.0.md`，版权人暂用 git 用户名 `TennousuAthena`，所有者可以改。这不是法律意见，标“待所有者评估”的都没有定论。
- **决策**：
  1. **项目自己写的代码和文档是 MIT。** 提交历史只有一个作者，仓库未公开，所以可以改。
  2. **这些部分仍是 GPLv3，单独标明**：`android/app/src/main/cpp/playfair/`（RPiPlay，原样）；`android/app/src/main/cpp/fairplay_jni.c`（回答表来自 RPiPlay）；FFmpeg 音频扩展 `org.jellyfin.media3:media3-ffmpeg-decoder`（预编译依赖）；`system/thinkos-cast/META-INF/com/google/android/update-binary`、`system/thinkos-certs/META-INF/com/google/android/update-binary`（同一份 Magisk 安装模板，原样复制，只在模块 zip 里）。LIC-04 另允许 `artifacts/lic/LIC-04/thinkos-ffmpeg-source-v1.9.0+1.tar.gz` 和正式 Release 同名附件存放该扩展及其两个子模块的完整上游源码，只作为独立存档，保留各自许可证；不解包或改写进 MIT 源文件。归档工具由本项目自己编写。
  3. **完整版 APK 作为一个整体按 GPLv3 发布**（GPLv3 第 5 条 c）。同一条也写明不影响单独获得的授权，所以别人从仓库单独拿 MIT 部分，仍然按 MIT 使用，可以用在闭源产品里。
  4. **发布 APK 就要提供完整源码**（第 6 条）：MIT 部分、构建脚本、FFmpeg 扩展的源码都算。给谁 APK 就要给谁源码，公开发布就等于公开源码，**不能只发 APK**；所以第一个公开的 OTA 之前，公开仓库必须已经在。这个方案的好处是别人能拿走 MIT 部分，不是让完整版少开源。
  5. **不含 GPL 的构建**：`-Pthinkos.ffmpeg=false` 和 `-Pthinkos.fairplay=false` 均已实现，双构建库清单通过（LIC-01）；设备 opt-out 回归待连接恢复。两个都关的 APK 没有 GPL 代码，可以不按 GPLv3 发；代价是没有 AirPlay 屏幕镜像，也解不了 AC-3 / E-AC-3 / DTS / ALAC。
  6. **没选的方案**：把 FairPlay 拆成独立的小 APK、自己编译 LGPL 的 FFmpeg。主 APK 可以不带 GPL，但多一个安装物和一条构建链。

## ADR-047 设备到设备的音视频通话（2026-11-04）

## ADR-049 蓝牙音箱（2026-11-04，草案）

- **决定**（所有者）：设备打开蓝牙后可以当蓝牙音箱，手机连上它的蓝牙就能把它当作蓝牙音频设备来播放。
